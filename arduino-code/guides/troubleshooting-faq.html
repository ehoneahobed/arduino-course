Troubleshooting FAQ

Symptom tables: dark LED, Verify errors, board not found, button stuck.

How to use this page: Run the Debugging playbook first (ordered steps). Then jump to the symptom table that matches. Fix one thing, re-test, then continue.

This aggregates the silent failures absolute beginners hit in Modules 0–3 (and early hardware). Lesson “Common mistakes” tables still matter — the playbook is the procedure; these tables are the detail.

Guide

1. Master order (do not skip)

Full procedure with Module 0–3 fast paths: Debugging playbook. Short reminder:

  1. Is the sim running? (Tinkercad: Start Simulation — not paused.) On hardware: did Upload succeed, not only Verify?
  2. Wiring / polarity / resistor? Pin → resistor → LED anode → cathode → GND. Resistor 220 Ω, not 220 kΩ. Breadboard: breadboard basics.
  3. Do pin numbers match? The wire’s pin, pinMode, and digitalWrite/digitalRead must agree. Prefer named constants (const int ledPin = 13;).
  4. Did Verify/compile succeed? Read the first red error; fix that before the rest.
  5. Serial baud / Monitor open? Sketch Serial.begin(n) matches Monitor baud; Monitor actually visible. See Serial how-to.
  6. Logic / blocking / polarity of if? Pull-up buttons read LOW when pressed. Long delay freezes everything else. Print values before blaming the LED.

3. Code will not Verify (compile errors)

You see something like…Likely meaning
was not declared in this scopeTypo in name; forgot to declare variable; wrong capitalization (LedPin ≠ ledPin)
expected ';' before…Missing semicolon on the line above the reported line often
Brace / “does not name a type” chaosMismatched { } — count them; copy starter again if lost
Folder / .ino name warningsSketch folder name must match .ino name (IDE)
Library header not found#include library not installed (IDE Library Manager) — or unsupported in Tinkercad

Habits:

  • Fix the first error first; later errors are often cascading noise.
  • Change one identifier spelling at a time.
  • Compare with the lesson starter’s structure (setup / loop present?).

Lesson refs: 0.2 Verify vs Upload; 0.4 anatomy of a sketch.

5. Button always HIGH or always LOW

Remember INPUT_PULLUP + button to GND:

PhysicaldigitalRead
Not pressedHIGH
PressedLOW
SymptomLikely cause
Always HIGHButton not connected to GND; wrong pin; not really closing
Always LOWPin shorted to GND; wired as if pull-down but code uses pull-up; stuck button
Inverted lamp logicif (reading == HIGH) when you meant “pressed” — pressed is LOW
Floating nonsense (random)Missing INPUT_PULLUP (or external pull)

Debug: Serial.println(digitalRead(buttonPin)); while pressing — do not guess. Lesson refs: 1.3 reading a button.

6. Button feels like many presses / multi-trigger

  • Contact bounce — real buttons chatter. Lesson 1.4–1.5.
  • In Tinkercad bounce may be too clean [TC†] — your desk kit will look worse; still learn debounce.
  • Using level (“is LOW”) instead of edge (“just became LOW”) can repeat actions while held.
  • Need one lastReading (or equivalent) per button — sharing one variable across two buttons causes ghosts.

Lesson refs: 1.4, 1.5, 2.5.

Guide

7. Everything freezes / UI ignores the button while blinking

Classic cause: long delay(...) chains. The board is busy waiting; it is not reading inputs.

  • Module 2 exists to replace that habit with millis() timing.
  • Temporary delay for Blink (Module 0) is OK; do not build Module 1–2 projects out of multi-second delays.

Lesson refs: 2.1 why delay blocks; 2.2 millis heartbeat.

12. Still stuck after the playbook?

  1. Duplicate the circuit; strip down to Lesson 0.3 LED-only.
  2. Prove HIGH lights the LED.
  3. Add back one feature at a time.
  4. Paste Serial output and your pin map when asking a human for help.

You are not expected to memorize hardware lore on day one — you are expected to run §1 before rewriting the whole sketch.
