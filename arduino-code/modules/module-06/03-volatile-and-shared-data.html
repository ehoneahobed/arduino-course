volatile and shared data

The compiler may cache a variable if it thinks nothing else changes it. An ISR changes it behind loop’s back — mark shared data volatile.

About 40 minutes. volatile ≠ atomic and ≠ debounce.

Start here

Learning outcomes

  1. Mark ISR-shared variables volatile and explain why.
  2. Use flag-in-ISR / work-in-loop: heavy work stays out of the ISR.
  3. Snapshot multi-byte values carefully so loop does not see a torn count.
Concept

Re-read from memory

Concept

volatile means “this can change anytime.” Without it, if (eventFlag) may optimize to always-false. It does not make operations atomic — use a brief noInterrupts window for multi-byte copies when precision matters.

Part

Flag + clear + work

volatile bool eventFlag = false;
void onBtn() { eventFlag = true; }

void loop() {
  if (eventFlag) {
    noInterrupts();
    eventFlag = false;
    interrupts();
    Serial.println("press");   // HEAVY WORK HERE
  }
}

// Snapshot a counter
noInterrupts();
unsigned long n = pulseCount;
interrupts();
Lab

Signal only in ISR

15 min

Project M6-L03-Volatile: D2 button. Add volatile; move Serial into loop. Success: ISR ≤ a few statements; every accepted event prints from loop.

Patterns

Defer heavy work

Pattern

ISR sets flag/count. loop clears and does Serial, LEDs, FSM, display. Snapshot wide counters under a short no-interrupt window.

Check

Check yourself

  1. Why does an ISR-shared flag need volatile?
    Model answer

    So the compiler re-reads memory and does not assume the value is unchanged.

  2. Where should Serial.println run — ISR or loop?
    Model answer

    loop (or other non-ISR context).

  3. What does noInterrupts/interrupts protect when clearing a flag?
    Model answer

    Clearing without losing a press that arrives mid-clear (critical section).

  4. volatile removes the need to debounce a mechanical switch.
