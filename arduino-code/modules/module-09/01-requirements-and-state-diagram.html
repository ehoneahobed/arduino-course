Arduino Coding  ·  Module 9  ·  Lesson 9.1  ·  Design

Requirements & state diagram

Choose one primary capstone. Write testable requirements and a complete state diagram before adding features. The design packet is the contract reviewers open first.

About 45–60 minutes. Mostly writing/drawing — little or no upload yet.

Start here

Learning outcomes

  1. Write user stories, an I/O list, and success criteria for one capstone (A–E).
  2. Draw a complete FSM state diagram (states, triggers, outputs) before features.
  3. Package those artifacts in a project README / sketch header.
Concept

Requirements, not wishes

Concept

A requirement is a testable promise. Capstone grades weigh behavior & requirements at 35% — write them first. User stories: As a … I want … so that … (3–7 for MVP). The I/O list names every pin role and safe defaults.

Part

Design packet

README top: primary letter, board, IoT path (none / MQTT / HTTP). Then MVP stories, I/O table with SAFE_LEVEL, and a diagram where every circle is a future enum, every arrow a labeled trigger, outputs noted per state.

CapstoneExample MVP story
A PlantDry-soil reminder; pump/relay off when idle
B GuardianArm/disarm; intrusion → ALARM with ack
C WeatherJSON telemetry; command one LED over MQTT
D ReactionReady/go/foul FSM; high score on display
E PointerPots move pan/tilt within soft limits

Success criteria (all): state diagram in README/header; no long interactive delay; debounced inputs; hardware demo evidence (TC share ≠ Module 9 credit).

Lab

Design packet only

40 min

Project folder M9-Capstone-<Letter>-<ShortName>/. Fill README: letter, stories (≥3), I/O, ASCII diagram, success checklist. Optional stub .ino with header comments only — no feature rush. Design review: mutually exclusive states, every arrow labeled, SAFE idle clear.

Patterns

Choose → specify → diagram → then code

Pattern

One primary capstone. Header/README as contract: wiring, diagram, SAFE defaults, and (if IoT) topic/URL plan.

Check

Check yourself

  1. How many primary capstones should you ship in Module 9?
    Model answer

    One (optional second only after the first passes).

  2. What three artifacts belong in the design packet before feature code?
    Model answer

    User stories, I/O list, state diagram (plus success criteria).

  3. Why separate stretch from MVP stories?
    Model answer

    Protects the vertical slice from feature creep; stretch stays optional.

  4. A Tinkercad-only design packet can replace the hardware demo in 9.5.
Watch outs

Common mistakes

MistakeFix
Coding features on day oneFinish README + diagram first
Vague storiesRewrite with observable verbs
Overlapping statesMutually exclusive enum names
I/O missing SAFE_LEVELDocument idle actuator levels
Choosing C without ESP32 / Gate DSwitch primary or finish Module 8
Two primaries at oncePark the second on stretch
