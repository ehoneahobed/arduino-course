Code structure & reuse

Extract after it works. One job per module. Thin loop. Structure & readability is 20% of the rubric.

About 50–70 minutes. Refactor the resilient slice — no new features.

Start here

Learning outcomes

  1. Extract a small reusable module (.h/.cpp or clear tabs) from your capstone.
  2. Document the module’s public API (functions, types, non-goals).
  3. Apply a code-review checklist for the 20% structure weight.
Concept

Reuse boundaries

Concept

A public API is what callers may use. Private helpers stay in the .cpp. If everything is public, you split files — you did not modularize. Packaging continues in 9.5.

Lab

One module extract

35 min

Pick one candidate. Extract, compile every step, wire the main sketch to the module. Structure-only — no new features. Optional peer pass on the checklist.

Patterns

Extract after it works

Pattern

One job per module — not UtilsEverything. Thin loop: events → fsm.handle → outputs/net. API comment block at the top of each .h.

Check

Check yourself

  1. When should you extract a module — before or after the slice works?
    Model answer

    After it works (post 9.2/9.3).

  2. What belongs in a .h public API comment?
    Model answer

    Responsibilities, how to call, non-goals, ISR rules.

  3. Name two items from the structure code-review checklist.
    Model answer

    e.g. diagram matches enum; thin loop; named pins; no secrets in git.

  4. Splitting code into files automatically earns the patterns rubric points.
