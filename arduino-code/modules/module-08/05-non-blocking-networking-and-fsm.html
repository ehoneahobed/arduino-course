Non-blocking networking + FSM

Networks are intermittent. Blocking while (!connected) freezes sensing. Treat link up/down as events feeding an FSM — sample in every powered state; publish only when ONLINE.

About 50 minutes. Desk ESP32 — toggle AP to test reconnect.

Start here

Learning outcomes

  1. Model Wi‑Fi (and optional MQTT) lifecycle as an enum FSM.
  2. Keep sensor sampling and local UI alive while the radio is down.
  3. Replace block-forever connect with timed retries driven by millis.
Concept

Why an FSM for networking?

Concept

Nested if (WiFi) pyramids and reconnect spam every loop become named states + one switch. Sample outside the “online only” branch. Print state name on enter.

Part

Suggested states

BOOT --> WIFI_CONNECTING --ok--> ONLINE --lost--> RECONNECT_WAIT
              |                      ^                    |
              +--timeout--> OFFLINE_HOLD ---retry---------+

MVP: WIFI_CONNECTING ⇄ ONLINE with RECONNECT_WAIT backoff. Timing: connect window ~15 s, retry ~10 s, sample always, publish only ONLINE.

Lab

Net FSM that keeps sampling

30 min

Project M8-L05-NetFsm. Draw the diagram in the sketch header. Starter stub → complete connecting/online/reconnect + continuous sampling. Kill AP 20 s — samples continue; reconnect recovers.

Patterns

Pattern stack

Pattern

enum NetState + enterState(); millis connect window + backoff; sensor sampleMs independent of net; optional MQTT only when ONLINE. Production connection managers → future esp32/.

Check

Check yourself

  1. Why is infinite while (!connected) delay(500) harmful in loop?
    Model answer

    It blocks sensing, UI, and buttons.

  2. Which work should continue in RECONNECT_WAIT?
    Model answer

    Sensor sampling (and local fail-safes) — not necessarily publish.

  3. What Module 5 habit belongs in the sketch header?
    Model answer

    State diagram (ASCII).

  4. Publish/telemetry must continue at full rate while offline.
